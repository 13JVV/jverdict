### 결과 1: 관광객 비교군은 쓸 수 없다 (설계 변경, 사후 결정임을 명시)
- 처음 설계는 삼중차분(도민·관광객 × 가능·불가 업종)이었다. 결과는 5월 점프 −0.187로, 효과가 음수로 나왔다.
- 원인: 관광객의 사용 가능 업종(음식점 등) 지출이 4월 0.49에서 5월 0.71로 급반등했다(전년동월비). 2020-04-30~05-05 황금연휴의 국내 관광 회복이 관광객이 쓰는 업종에만 몰렸다. 관광객 쪽 차분이 업종별로 다른 관광 회복을 빼 버려 가정이 깨진다.
- 그래서 **도민 내부 이중차분(가능 업종 − 불가 업종)**으로 바꿨다. **이 변경은 데이터를 본 뒤에 내린 결정이다.** 판정서에 그대로 적고, 처음 설계의 결과도 함께 보고한다.

### 결과 2: 도민 내부 이중차분
5월 점프 = 5월 격차 − 직전 기준 기간 격차 (전년동월비 로그). p값은 위약 60개월 대비 순위 p값.

| 대조 업종 | 기준 1개월 | 기준 2개월 | 기준 3개월 |
|---|---|---|---|
| 대형종합 + 유흥 | +6.4% (p=0.21) | +5.7% (p=0.21) | +3.0% (p=0.30) |
| 대형종합만 | +8.2% (p=0.13) | +8.2% (p=0.15) | +3.7% (p=0.28) |
| 대형종합 + 유흥 + 면세 | +5.1% (p=0.25) | +3.3% (p=0.34) | +1.3% (p=0.41) |

- 격차 추이(대형종합 + 유흥): 2월 +0.223, 3월 +0.153, 4월 +0.140, **5월 +0.202**, 6월 +0.082, 7월 +0.132
- 9개 설정 모두 **방향은 양수**다(+1.3% ~ +8.2%). 하지만 **위약 분포 대비 유의하지 않다**(p 0.13~0.41).
- 업종 부호 검정: 가능 업종 22개 중 19개(86%)가 5월에 올랐다. 위약 월 평균은 51%, 순위 p=0.115다.
- 이중 계산: pandas와 SQL 결과가 일치한다.

### 결과 3: 업종별 (KDI 비교)
- 5월에 많이 오른 업종: 수산물 +0.32, 욕탕 +0.28, 육류 +0.20, 일식 +0.15, 한식 +0.10

### 해석과 판정 후보
- **방향과 시점은 KDI와 같다.** 5월에 일시적으로 늘었다가 6월에 사라졌다. 폭도 대부분의 업종에 걸쳐 있다.

- 개선안: C1의 p가 0.01 미만이면 판정 상한을 '판정 보류'로 둔다. 다만 추세를 보정한 추정(사전 추세 외삽 대비 단절)이 유의하면 '조건부'로 올린다.
- 이 개선안은 Agent 판정 규칙에 반영하고, 반영 시점과 이유를 기록한다.

### 실데이터 사례 종합 (현재)
| 사례 | 판정 | 엔진이 보여 준 것 |
|---|---|---|
| A 청소년 버스 무료 | 판정 보류 | 측정 체계 변경(무료 승차 누락) 탐지 |
| B 1차 재난지원금 | 조건부 | 방향은 일관되나 검정력 부족, 비교군 오염(황금연휴) 탐지 |
| D 중국 단체관광 재개 | 판정 보류 / 조건부 | 데이터 결측 탐지, 사전추세 위반으로 과대 추정 차단 |

### 내일 논의할 것: 정상 판정 사례를 어떻게 확보할까
1. 사례 B를 '조건부'의 실제 예시로 쓰고, '효과 있음'은 합성데이터(사례 C)로만 보여준다.
2. 같은 카드 데이터로 더 강한 정책을 찾는다. 후보: 2021-09 상생 국민지원금(소득 하위 88%, 9월~12월)과 2021년 제주 자체 지원금. 단, 이번 탐색은 사전 계획이 아니므로 결과를 보기 전에 분석 설계를 먼저 고정한다.
3. 주분석 설계를 데이터를 보기 전에 정하는 규칙(사전 등록)을 Agent에 넣어, 오늘 같은 사후 설계 변경을 자동으로 표시하게 한다.

## F9. Agent 완성: 6역할 상태머신, 템플릿·Claude·재실행 모드 (2026-11-03)

코드: `src/jverdict/agent/` (catalog, library, design, tools, llm, prereg, roles, orchestrator, demo) · 테스트 72개 통과(Agent 14개)
실행: `python -m jverdict.agent "질문"` (템플릿, 오프라인) · `--mode claude` · `--replay outputs/runs/<실행 번호>` · 사례 일괄 `python -m jverdict.agent.demo [--claude]`
결과: `outputs/runs/case-<사례>-<모드>/` (카드·점검·사전 등록·잠금·분석·반론·판정서·manifest·LLM 캐시·이벤트 로그), 요약 `outputs/runs/_summary.md`

### 구조와 가드레일 (코드가 강제)
- 순서 고정: parse → confirm(사람 확인 1회) → scout → design → lock → execute → skeptic → report → manifest. 앞 단계를 거치지 않으면 GuardError.
- 효과 가림: Design 단계 툴은 정책 시행일 이전 자료만 돌려준다. 품질 점검은 측정 단절이 의심될 때만 변화 크기를 보여 준다.
- 잠금: 설계 문서 + 설계 JSON의 SHA-256. 실행 직전에 다시 계산해 다르면 멈춘다. 잠금 뒤 변경은 변경 기록(이유·바뀐 항목·새 지문). 기존 사전 등록 사례(B·D)는 `docs/prereg` 잠금 지문도 확인한다.
- 효과 추정 툴(extra_check)은 잠금 뒤 Skeptic 단계에서만 쓸 수 있다.
- 반론의 성립 여부는 코드가 정한다(같은 방향·유의·크기 절반 이상 유지면 기각). 판정 규칙 밖의 반론이 성립하면 하향(효과 있음 → 조건부, 효과 없음 → 판정 보류).
- 서술 숫자 대조: Reporter 문장 속 숫자가 사실 목록(툴 결과)에 없으면 다시 쓰게 하고, 두 번 실패하면 템플릿 서술로 대체한다(달 이름 'N월'은 예외).
- 비밀값: 키는 config.get_secret으로만 받고, 로그·오류에서 키 모양 문자열·실제 키 값·URL 키 파라미터를 지운다. Claude에는 집계 요약만 보낸다.
- 실패 처리: Claude 단계가 실패하면 그 단계만 템플릿으로 대체한다. 크레딧·인증·연결 오류면 남은 단계는 바로 템플릿으로 진행한다.

### SDK·모델 적용 (claude-sonnet-5-5, effort medium)
- 강제 tool_choice가 400이라 auto + strict 툴 + `output_config.format`(JSON 스키마)으로 역할별 결과를 받는다.
- 응답 블록은 고치지 않고 그대로 대화에 붙인다(사고 블록 보존). 스트리밍으로 받고(`messages.stream` → `get_final_message`) max_tokens 32,000.

## F11. Windows 설치 묶음·설치 점검, 재현성 보강 (2026-11-05)

코드: `tools/build_bundle.py`(묶음 만들기) · `src/jverdict/doctor.py`(설치 점검) · `src/jverdict/data/sources.py`(원본 지문 기록) · `실행.bat`·`점검.bat`·`설치.bat`
테스트: 98개 통과(이번에 16개 추가) · 문서: `docs/manual/설치_실행.md`, `docs/test/Windows_시험표.md`

### 설치 묶음 (`dist/JVerdict_win64_<날짜>.zip`, 215MB, 풀면 552MB)
- **설치가 없다.** python.org 공식 Windows 임베디드 Python 3.14.3을 넣는다. 공개 SHA-256과 대조한다.
  Windows용 wheel 59개는 개발 PC에서 `runtime/Lib/site-packages`에 미리 풀어 둔다. 받는 PC에는 인터넷·관리자 권한·Python이 필요 없다.
  `python314._pth`는 `Lib\site-packages`와 `..\src`만 가리킨다. 그래서 사용자 PC에 다른 Python이 있어도 섞이지 않는다.
- **버전은 개발 PC와 같게 고정한다**(`requirements/lock-win-cp314.txt`). 판정 기록을 만든 환경과 같아야 수치가 재현되기 때문이다.
- **빌드 중 발견:** pip의 `--platform` 설치는 의존성 조건(marker)을 개발 PC(macOS) 기준으로 판단한다.
  그래서 Windows에서만 필요한 `colorama`(pytest)와 `watchdog`(Streamlit)이 빠졌다. 그대로 뒀다면 Windows에서 화면이 뜨지 않았을 수 있다.
  빌드 도구가 설치된 패키지의 의존성을 Windows 조건으로 다시 따져 빠진 것을 채운다(시험 포함).
- **원본 CSV는 싣지 않는다.** 1.1GB 버스 원본 대신 가공 파일(parquet 63MB)을 싣는다.
  manifest의 데이터 지문은 원본 기준이므로, 원본이 있는 PC에서 '원본 지문 ↔ 가공 파일 지문' 짝을 `data/processed/_sources.json`에 적어 둔다.
  원본이 없으면 가공 파일 지문을 다시 계산해 이 기록과 맞을 때만 원본 지문을 쓴다. 가공 파일이 바뀌면 오류로 멈춘다(시험 포함).
  그 결과 원본이 없는 PC에서도 `data_equal`이 참으로 나온다.
- **검사에 하나라도 걸리면 압축하지 않는다.**
  - `.env` 파일 0개 · 실제 키 값 0건(값은 메모리에서만 비교) · 키 모양 문자열 0건(시험용 가짜 1건 허용)
  - Windows용이 아닌 바이너리(.so/.dylib) 0개
  - 배치 파일: CRLF·BOM 없음·`/dev/null` 없음·`chcp 65001`
  - 경로 길이: 묶음 안 최장 150자. 압축을 푸는 위치가 109자 이내면 260자 한도 안
  - 압축 CRC와 한글 파일 이름 UTF-8 표시
- **받은 PC 흉내:** 압축을 새 폴더에 풀고 원본 CSV가 없는 상태에서 점검을 끝까지 돌린다. 결과는 통과 21 · 주의 0 · 실패 0이다.
  `--full`(파일 1만 1천여 개 SHA-256 전체 대조, 템플릿 기록 재실행)은 통과 25이고, 묶음 폴더 안에서 돌린 자동 시험 98개도 모두 통과했다.
  Windows 실행 파일 자체는 Windows에서만 시험할 수 있다(사용자 시험표).
- 패키지 시험 코드(numpy·pandas·scipy·statsmodels·pyarrow의 `tests/`)와 Jupyter 확장을 빼서 88MB를 줄였다.

### 재현성 보강 (발견한 문제 3건)
1. **마지막 비트 차이는 같은 PC에서도 생긴다.** F10에서는 실행 환경 차이로 보았지만 아니었다.
   같은 Mac에서 `case-D-claude` 재실행만 따로 돌리면 6회 호출 중 2회가 정규화 지문(key_norm)으로만 맞았다.
   A·B 재실행 뒤에 이어 돌리면 6회 모두 정확한 지문이 맞은 적도 있었다.
   **같은 프로세스에서 앞서 무엇을 실행했는지에 따라** 부동소수 합의 마지막 비트가 달라진다(배열 메모리 정렬에 따른 SIMD 합산 순서 차이로 추정).
   원본 정밀도 해시만으로는 재현을 보장할 수 없다는 뜻이다. 정규화 지문이 필요하다는 판단을 확인했다.
2. **옛 Claude 기록에 key_norm을 채웠다**(`python -m jverdict.agent --backfill-key-norm`). API는 호출하지 않았다.
   재실행해서 모든 호출이 정확한 지문(입력이 비트 단위로 같음)으로 맞고 수치·판정까지 같을 때만 쓴다. 이때 지금 계산한 key_norm이 곧 원래 입력의 key_norm이다. 응답과 기존 지문은 건드리지 않는다.
   그 결과 A 9건, B 7건, **D 6건**을 채웠다. `case-D-claude`도 이제 실행 순서와 관계없이 재현된다. **크레딧 없이 복구했다.**
   Windows처럼 BLAS·CPU가 다른 PC에서도 같은 원리로 재현될 것으로 본다. `점검.bat`이 확인한다.
3. **재실행 폴더 이름.** 폴더 이름을 바꾼 기록(`case-C-claude-nocredit`, manifest의 run_id는 `case-C-claude`)은 재실행 결과가 다른 이름(`case-C-claude-replay`)으로 저장됐다.
   그래서 판정서·요약표가 짝을 못 찾았고, 빌드 도구는 이 폴더를 '짝 없는 재실행'으로 잘못 걸렀다.
   이제 재실행 폴더와 화면의 실행 번호는 원래 실행의 **폴더 이름**을 따른다(시험 포함).
- 그 밖에 Windows 대비:
  - 코드 지문을 CRLF/LF와 경로 정렬 방식에 무관하게 바꿨다(LF 파일만 있으면 예전 값과 같다).
  - 시각 기록을 `time.strftime('%z')` 대신 datetime으로 만든다(Windows에서는 지역화된 시간대 이름이 나올 수 있음).
  - Chrome·Edge를 사용자별 설치나 다른 드라이브에서도 찾는다.
  - 화면을 처음 실행할 때 Streamlit이 이메일을 묻고 멈추지 않게 했다(`showEmailPrompt=false`).
  - 포트가 사용 중이면 다음 빈 포트로 연다.
  - 실행.bat의 `1>/dev/null`(Windows에 없음)을 고쳤다.

## F12. 실데이터 양성 대조(사례 E): 사회적 거리두기 전면 해제 → 판정 보류 (2026-11-06)

- **목적**: 실데이터 3건(A·B·D)이 모두 '판정 보류'였으므로, 효과가 있다고 널리 알려진 정책으로 엔진이 실데이터에서도 효과를 찾아내는지 확인했다.
- **사전 등록**: `docs/prereg/case_distancing_2022.md`. 2026-11-06 00:30에 잠갔다(SHA-256 `f1dc11cb…`). 잠근 뒤 엔진을 실행했다.
  열람 고지: 같은 카드 파일을 B·D에서 썼다. 2022년 주점·식료품 금액은 보지 않았다.
- **설계**: 제주도민 × 주점(일반유흥 + 기타 주점) 대 식료품 소매 5업종의 로그 격차를 쓴 단절 시계열이다.
  - 사전 2021-04~2022-03, 사후 2022-04~09.
  - 계절 차분은 쓰지 않았다. 과거 같은 달도 방역 기간이라 기준값이 오염되기 때문이다.
  - 가짜 시행일은 코로나19 방역 기간(2020-02~2022-04)과 겹치지 않는 창에서만 뽑았다.
- **결과: 판정 보류**(`outputs/runs/case-E-template`).
  - 추정 +201%, 판정 구간 −66%~+2586%.
  - 검증 C0~C4는 모두 통과했다. 시점 위약에서는 가짜 34개 중 실제가 가장 컸다(순위 p=0.029, 위약 표준편차 0.05). 공간 위약(화장품·건강식품 −10%, 잡화 −9%)과 이중 계산도 통과했다.
  - 다만 분석적 표준오차가 1.03(로그)으로 커서 구간이 0을 포함했다. 판정 규칙 v2에 따라 '보류'다.
  - 규칙대로 그대로 보고한다. 결과를 본 뒤 설계를 바꾸지 않았다.
- **원인 진단** (수치는 대상/대조 로그 격차):
  - 2019년 정상 수준은 −1.5~−1.6이다. 사전 12개월 중 **2021-08이 −7.13**이다(사전 중앙값보다 4.44 낮음). 주점 결제가 거의 사라진 달이다.
  - 이 무렵 제주는 거리두기 4단계였다(9-12까지 연장 보도: 더팩트 2021-08). 4단계 지침에는 유흥시설 집합금지가 들어 있다. 제주 공고 원문은 확인하지 못했다.
  - 이 한 달이 기준선을 끌어내려 추정을 키웠고(+201%), 동시에 잔차 분산을 키워 구간을 넓혔다.
  - 직전 석 달(2022-01 −3.07, 02 −2.74, 03 −2.36)은 단계적 완화로 이미 오르는 중이었다. 해제 뒤 6개월(−2.02~−1.92)은 2019년 수준보다 여전히 낮다.
- **해석**:
  - "주점 소비 3배"라는 큰 숫자가 나와도 판정관은 결론을 내지 않았다. 기준 기간이 '같은 종류의 더 강한 조치(영업 금지)'로 오염되어 있었기 때문이다. 단순 전후 비교였다면 "+201%, 정책 효과 확실"로 썼을 것이다.
  - **양성 대조에서 '효과 있음'을 확인하지는 못했다.** 결과 설명자료에 그대로 적는다. '효과 있음' 판정이 작동한다는 증거는 여전히 합성데이터(C)다.
- **엔진·서술 보강** (이 사례에서 드러난 문제. 판정 규칙과 수치는 그대로다):
  1. **보류 이유 설명**: 월 단위에서 사전 기간의 크게 벗어난 시점(로버스트 z>5)이 사전 변동의 절반 이상을 차지하면, 판정서는 "사후 5524개월 필요" 대신 그 시점을 이유로 든다(`power.pre_outliers`). 필요한 데이터로는 그 시점의 원인 확인 자료를 안내한다. 일 단위는 적용하지 않는다(명절 하루 같은 이상은 HAC가 다룬다).
  2. **템플릿 요약**: "검증 항목을 모두 통과했습니다. 최종 판정은 판정 보류입니다."가 모순처럼 읽혔다. 이제 "검증은 모두 통과했지만 구간이 넓어(검정력 부족) 결론을 미룹니다"로 쓴다.
  3. **계절 처리 선택**: 등록 설계에 `season: none`을 둘 수 있다. Claude 툴 스키마에는 넣지 않았다(기존 기록의 재실행 지문 보존).
- **기록 재현성 보강** (사례를 하나 더한 것만으로 Claude 기록 3건의 재실행이 깨져서 고쳤다):
  - Policy Parser 프롬프트의 참고 사례 목록에 E가 더해져 A·B·D의 첫 호출 지문이 바뀌었다. 참고 목록을 A·B·D·C로 고정했다. 이후 사례는 코드가 핵심어로 연결하고 시행일·대상을 등록본으로 맞춘다.
  - D의 Claude Skeptic이 사건 달력을 2022~2025로 조회했는데, 새로 넣은 2022년 사건이 결과에 더해졌다. 사건에 '추가일'을 두고, 재실행은 원래 실행 날짜의 달력(`calendar_as_of`)을 쓴다.
  - 결과: 템플릿 5건, Claude 기록 4건 모두 재현된다.

## F13. Phase 6 데이터 사용 대조와 보강 (2026-11-06)

- 데이터 활용 명세를 쓰기 전에 기획서의 '쓰임'과 코드를 하나씩 대조했다. 기획서 v1.0까지의 표에는 실제로 쓰지 않은 쓰임이 적혀 있었다.
  - 일별 시간대별 버스 파일: '통학 시간대 점검'으로 적었지만 적재만 했다.
  - 시간대별·요일별 카드 파일: '교차 점검'으로 적었지만 구조만 확인했다.
  - 정류소 API: '지역별 분석'으로 적었지만 확보만 했다.
- 보강:
  1. **일별 시간대별 버스 파일을 사례 A 교차 점검의 네 번째 파일로 넣었다**(`jverdict.cases.quality_real`).
     - 측정 단절 진단: 청소년 −67%, 어린이 −57%로 둘 다 '의심(강)'. 경로·장애는 단절 없음.
     - 시간대별로 보면 청소년 감소(일반 대비)가 통학 시간대(07~09시 −69%)만이 아니라 새벽(−80%)과 밤(−69%)까지 고르다. 이용 행동이 바뀌었다기보다 집계에서 빠진 모양과 맞는다.
  2. **시간대별 카드 파일로 사례 E 보조 확인**(`jverdict.cases.distancing_night`, 사전 등록 밖, 판정에 쓰지 않음).
     - 제주도민 카드 소비 중 밤 시간대 비중: 2019년 5~9월 11.5%, 2021-08 4.5%, 해제 직전(2022-01~03) 4.4%, 해제 뒤(2022-05~09) 9.6%, 1년 뒤 9.1%.
     - 다른 파일에서도 해제 뒤 늦은 시간 소비가 두 배 넘게 회복했다. 사례 E의 '보류'는 효과가 없다는 뜻이 아니다. 기준 기간 설계(업종 파일의 2021-08) 때문에 판정관이 보수적으로 멈춘 것으로 읽는다. 판정은 바꾸지 않는다.
  3. 요일별 카드 파일은 이용자 구분(도민·관광객)이 없어 사례의 비교군을 만들 수 없으므로 쓰지 않는다. 정류소 API는 확보만 했다. 두 가지 모두 기획서와 데이터 활용 명세에 그대로 적는다.
- 그 결과 기획서 표현을 "8종 확보·점검, 그중 6종을 판정·교차 점검에 사용"으로 고쳤다.
